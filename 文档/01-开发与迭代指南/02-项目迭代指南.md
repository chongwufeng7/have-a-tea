# 项目迭代指南：流程、所需文档与结构

适用：原型、开发中或上线后的项目｜版本：WF-1.0.1｜更新：2026-10-07｜状态：生效

## 1. 迭代入口
用户反馈、测试缺陷、实际数据、平台变化、底座升级均可触发。先区分事实和猜测；没有数据不能把个别反馈说成全体用户结论。建议记录问题池，不自动获得开发授权。

优先级：P0 阻断运行/数据丢失；P1 核心流程错误；P2 体验问题；P3 可选改善。依据影响范围与证据排序，不能仅按开发方便排序。紧急修复可简化单据但不可省略范围、验证、回退和留档。

## 2. 固定步骤与输出
| 步骤 | 必做工作 | 输出/通过条件 |
|---|---|---|
| I0 收集 | 来源、复现、影响、证据、事实/假设 | ISSUE进入问题池；去重关联 |
| I1 定范围 | 选本轮处理项、目标、非目标、验收标准 | ITER单；新增规则/功能得到用户授权，范围内修复直接推进 |
| I2 分析影响 | 模块、配置、存档、广告、其他项目、兼容性 | 实施与回退方案；记录起始代码版本/快照 |
| I3 修改 | 按已定范围实现，不夹带额外优化 | 修改代码/配置；同步需求、规则、资源规范 |
| I4 验证 | 针对修改验证；回归受影响功能；必要时真机和体验验收 | TEST实际结果与证据；阻断缺陷未解决不得标通过 |
| I5 交付 | 变更说明、遗留项、运行方式、回退方法 | 版本记录、状态更新；区分技术完成和用户体验验收 |
| I6 观察 | 对照目标收集数据/反馈，决定保留、调整或回退 | ITER结论；不足则待观察，有后续问题再入池 |

状态：草案→待决策（仅需要时）→实施中→验证中→已交付→待观察/已关闭；也可阻塞、取消、回退。技术交付不等于收益或留存提升已证实。

### 上传前代码加固（微信小游戏发版轮次适用）
适用条件：本轮需要把代码上传到微信后台（提审或发版）。日常开发迭代不做加固。

顺序：
1. 改代码 → `npm test` → 开发者工具编译，确认游戏正常。
2. 核对包体余量：微信小游戏主包上限 4MB；加固按平台说明平均膨胀 30% 以内，加固前先算余量，不足则先压图再加固。
3. 在 `minigame/js/` 的 js 上右键 →「添加到加固文件列表」→ 选混淆程度、开启文件水印 →「全部加固」。插件为编辑器扩展「游戏深度保护」（codeFortify），入口：设置 → 扩展设置 → 编辑器扩展。
4. **加固后必须重新编译，确认模拟器仍能正常运行**，未验证不得上传。
5. 上传 → 记录版本号与平台返回信息。
6. 上传后执行 `git checkout -- minigame/js/` 恢复源码。

禁止事项：加固会改写 js 源文件，混淆后的代码不得提交进 Git；仓库中的干净源码即为回退依据。加固未做、加固后未编译验证、上传后未恢复源码，均需在 ITER 中记录为未完成项，不得写作已通过。

## 3. 不同改动的验证范围
| 分类 | 更新文档 | 最小验证 |
|---|---|---|
| 规则缺陷 | 规则、测试、迭代单 | 复现用例、修复结果、受影响胜负/道具；必要自动测试 |
| 关卡数值 | 参数来源、假设、迭代单 | 配置合法性、可解性、代表关卡试玩；效果指标待真实数据 |
| 美术/布局 | 资源规范、来源授权 | 实际尺寸、识别、触控、遮挡和设备适配；无需镜像实现的无效测试 |
| 广告/平台 | 架构、平台配置、发布说明 | 完整观看/取消/失败/重复回调/换关、前后台与真机 |
| 底座升级 | 依赖版本、影响项目清单 | 每个受影响项目回归，存档兼容，不自动全量替换 |
| 文档/目录整理 | 导航、状态、流程记录 | 路径和链接、启动、必要现有测试；不重测无关玩法体验 |

## 4. 每轮输出文档及结构
### A. 迭代问题池（长期维护）
字段：ISSUE编号、来源日期、现象、证据、事实/假设、影响、优先级、状态、关联ITER、结果。关闭必须指向实际结果。

### B. ITER-xxx.md（一轮一份）
1. 基本信息：项目、流程版本、起始/目标版本、状态、关联问题。
2. 问题依据：复现、证据、待验证假设。
3. 目标范围：本轮做什么、不做什么、验收标准及授权来源。
4. 影响方案：文件/模块、存档兼容、跨项目影响、实施与回退。
5. 验证：测试编号、版本环境、实际结果、证据、未测项。
6. 交付结论：完成项、遗留项、用户验收、观察结论、关闭条件。

### C. 现有文档同步（不另建重复副本）
项目状态、版本决策每轮更新；需求/规则/架构仅影响到时更新；测试明细写验收文档，ITER用编号引用。配置是数值唯一来源。

## 5. 目录与命名
```text
文档/
├─ 01-开发与迭代指南/02-项目迭代指南.md
├─ 01-开发与迭代指南/模板/07-迭代单模板.md
├─ 03-迭代记录/
│  ├─ 00-迭代问题池.md
│  ├─ ITER-001.md
│  └─ ITER-002.md
└─ 04-测试与验收/00-测试与验收记录.md
artifacts/版本号/ （截图、日志、可交付包）
```
编号顺延不重用。取消单也保留原因。避免多个“最终版”，采用版本记录与版本控制；未建版本控制时先记录可靠基线，不能声称有提交可回退。

## 6. 示例：反馈第10关太难
ISSUE记录一次反馈及卡住位置→检查可解性和实际操作→提出参数修改与预期→记录配置差异→验证有解并试玩→交付→有真实样本后判断难度是否改善。不能只降低牌数就写“留存提升”。

## 7. 工作流自身也要迭代
工作流任务记录 WF 版本、变化、适用时点、已有项目需补齐项。开发任务在每轮/阶段开始核对版本；中途变化在下一安全检查点核对。禁止并发覆盖同一文件，禁止把新要求伪装成旧版本已测过。
